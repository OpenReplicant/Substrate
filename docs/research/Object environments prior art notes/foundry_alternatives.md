# Open-source and self-hostable systems resembling Palantir Foundry's Ontology (as of 2026-11-23)

Method note: licences and release/activity data below were read from the GitHub API (repo metadata, latest release, LICENSE files via `gh api`) on 2026-11-23 unless marked. Where GitHub reported NOASSERTION I read the LICENSE file head. Palantir facts come from palantir.com/docs fetched through a summarising fetch tool, so they are second-hand paraphrase of the primary pages. Vendor blogs and "open-source Palantir" articles are treated as claims.

## 1. What exactly is Palantir's Ontology model?

### Takeaway
Palantir defines the Ontology as an operational layer over datasets, virtual tables and models, with a semantic half (object types, properties, link types) and a kinetic half (action types, functions, dynamic security). Agents reach it through the OSDK, the Ontology MCP (OMCP) and Palantir MCP.

### Cited Findings
- The Ontology is "an operational layer for the organization", sitting on top of datasets, virtual tables and models and connecting them to real-world counterparts. Semantic elements: objects, properties, links. Kinetic elements: actions, functions, dynamic security. — [Palantir Ontology overview](https://www.palantir.com/docs/foundry/ontology/overview/)
- Datasources are mapped into "objects, properties, and links". Interfaces are Ontology types describing the shape of an object type and its capabilities, giving polymorphism across object types. — [Palantir Ontology overview](https://www.palantir.com/docs/foundry/ontology/overview/)
- Functions "provide a way to author and evolve business logic with arbitrary complexity". — [Palantir Ontology overview](https://www.palantir.com/docs/foundry/ontology/overview/)
- An action type defines a set of changes to objects, property values and links applied in one step plus side effects. Each action is "a single transaction that changes the properties of one or more objects". Components: rules (the changes), parameters (form inputs), submission criteria (validation, separate page), permissions (who may run it), side effects (notifications, webhooks), function-backed actions. — [Palantir action types overview](https://www.palantir.com/docs/foundry/action-types/overview/)
- Writeback: committed edits show in all applications, and the latest object data with user edits is stored in the object type's writeback dataset. — [Palantir action types overview](https://www.palantir.com/docs/foundry/action-types/overview/)
- OMCP exposes "your application's ontology resources (such as object types, action types, and query functions)" as MCP tools; agents can read objects, run predefined actions and query data. Which actions an agent may take is restricted through application restrictions and permissions. — [Ontology MCP overview](https://palantir.com/docs/foundry/ontology-mcp/overview/)
- OMCP is a Developer Console feature, described as beta, limited by application scopes; Palantir MCP (builder-oriented) can modify ontology types but cannot write ontology data; OSDK generates Python, Java and TypeScript SDKs from an ontology. Warning on the OMCP page: with LLMs hosted outside AIP, Palantir data is exposed to an external client. — search summary of [Palantir developer docs](https://palantir.com/docs/foundry/ontology-mcp), [Palantir MCP](https://palantir.com/docs/foundry/palantir-mcp/), [pro-code agents](https://palantir.com/docs/foundry/agents/overview/), [announcements 2026-07](https://www.palantir.com/docs/foundry/announcements/2026-07). Beta status not confirmed on the fetched OMCP overview page itself.
- Palantir does not open-source Foundry; only client SDKs (e.g. an Apache-2.0 Python SDK) — summarised in a web search answer, not verified against the SDK repo.

### Inferences
- The model reduces to six ideas a Postgres build can copy: typed object, typed property, typed link, interface (shared shape), action (validated, permissioned, transactional edit with side effects), function (logic). The agent seam is "agents get only actions and reads the Ontology exposes, under scoped credentials".
- The key distinction to copy is that agents write only via actions, never raw tables.

### Gaps
- Exact submission-criteria and permission semantics (object security vs property security vs marking) not read in detail; the fetch tool returned only the overview pages.
- Whether OMCP is still beta in Nov 2026 not confirmed.

## 2. Projects that position as Foundry/Ontology alternatives

### Takeaway
Nothing found is a mature, adoptable Foundry Ontology. The closest by shape (OpenFoundry) has a vanished GitHub repo and a conflicting licence; the most popular (Semantica) is a knowledge-graph toolkit without actions or permissions. Copy the ideas, do not plug these in.

### Cited Findings
- **OpenFoundry (DioCrafts)**: self-hosted "operational data platform", Go microservice monorepo plus React 19 frontend, protobuf-generated SDKs, modelled on Foundry's documented capability areas. Docs site lists object types, properties, link types, actions, functions, interfaces; actions go through validation, authorization, audit, with validate/execute/batch-execute/what-if endpoints — [SourcePulse aggregator](https://www.sourcepulse.org/projects/30129680), docs index via search results at [diocrafts.github.io/OpenFoundry](https://diocrafts.github.io/OpenFoundry/). **Verified problem**: `gh api repos/DioCrafts/OpenFoundry` returned 404 on 2026-11-23 (removed, renamed or private), and the docs subpages I tried returned 404. Licence conflict: docs claim Apache-2.0 (per search summary); Gitee mirror README says "AGPL-3.0-only", 1 star, 1,003 commits, no releases — [Gitee mirror](https://gitee.com/zdy336/OpenFoundry). Gitee notes "41 Go microservices"; whether it works end to end is not shown. Storage not verified. MCP not found. Status: do not depend; AGPL if the mirror is right.
- **Semantica** (now `semantica-agi/semantica`, was Hawksight-AI): MIT (GitHub API), 14.7k stars, latest release v0.7.0 on 2026-09-22, pushed today. Ships OWL generation, SHACL validation, SKOS, a visual editor, an ontology hub, decision records and a policy rule engine, plus an MCP server (`semantica-mcp`) exposing entity/relation extraction, decision recording and lookup, graph query/update, reasoning, export. Graph stores: Neo4j, FalkorDB, Apache AGE, Neptune, Oxigraph, Blazegraph, Jena, RDF4J; pgvector only as a vector store; no Postgres relational store listed. No action types described and no access-control model described (only an API key env var). — [Semantica README](https://github.com/Hawksight-AI/semantica) (redirects to the new org). "Tops GitHub Trending" is a claim from [besthub.dev](https://www.besthub.dev/articles/open-source-palantir-tops-github-trending-ontology-becomes-the-next-agent-layer-80399353f094), not checked.
- **agent-utilities**: the repo `Knuckles-Team/agent-utilities` now resolves to `Knuckles-Team/meristem` (MIT, 5 stars, Python, v5.0.0 released 2026-10-30), described as "An agent factory leveraging Pydantic AI and Pydantic AI Harness". The comparative-analysis page against Foundry returned 404 (old URL and new). README mentions typed actions/observations, a policy gate, MCP/REST/A2A — [meristem repo](https://github.com/Knuckles-Team/meristem). I found no evidence it now ships an ontology layer; treat the ontology claim as unverified. Negligible adoption.
- **Open Ontology SDK (OOSDK)**: a personal project described in an article; page returned 403 so I could not read it; status unconfirmed — [article](https://levelup.gitconnected.com/why-im-building-an-open-ontology-sdk-and-what-palantir-got-right-about-ai-orchestration-b68830a6b41f).
- **ibl.ai "agentic ontology"**: vendor blog claims MIT-licensed, self-hosted, MCP exposure — [ibl.ai blog](https://ibl.ai/blog/palantir-ontology-alternative-self-hosted). Guessed repo `ibl-ai/agentic-ontology` does not exist on GitHub (404). Vendor claim only; unverified.

### Inferences
- Of these, only Semantica has real adoption and a verified permissive licence, but it covers the semantic (knowledge graph) half, not the kinetic half (actions, permissions) and not Postgres.
- OpenFoundry's design (validate / execute / what-if on actions, audit) is a useful spec to copy even if the code cannot be used.

### Gaps
- OpenFoundry's current location and real licence; storage layer.
- agent-utilities' former ontology implementation (history of the renamed repo not inspected).
- OOSDK and ibl.ai code could not be located.

## 3. Adjacent mature systems (licence, maturity from GitHub API 2026-11-23)

### Takeaway
Postgres-native, permissively licensed building blocks are PostgREST, Supabase (Apache-2.0 repo), pgmq, Hasura v2; the objects-with-gated-actions part is best copied rather than adopted. Several popular no-code/CMS options are source-available or AGPL and fail the default-licence test.

- Postgres RLS / roles as the permission model, verified: Supabase (grants + policies on `anon`/`authenticated`; with a user token the request runs under that user's policies; no policy means no rows) — [Supabase RLS docs](https://supabase.com/docs/guides/database/postgres/row-level-security). PostgREST is the engine Supabase's Data API is built on (from background knowledge; my direct fetch of PostgREST docs returned 429, not verified this session). Odoo uses Postgres but its own ACL/record-rule layer, not RLS (background knowledge).
- Postgres MCP servers built around per-user roles and RLS: pgEdge Postgres MCP Server (maps each MCP user to a Postgres role so RLS filters rows; launched April 2026) — [pgEdge docs](https://docs.pgedge.com/pgedge-postgres-mcp-server/v1-0-0/advanced/row-level-security/); pgguard runs `SET LOCAL ROLE` per transaction so grants and RLS hold — [pgguard listing](https://glama.ai/mcp/servers/Azzaraell/pgguard-mcp). RLS covers SELECT/INSERT/UPDATE/DELETE only, not DDL; the prompt-injection problem is mitigated but not solved by the database layer — [Composio](https://composio.dev/blog/supabase-mcp-server-connecting-ai-agents-to-your-database), [Bytebase review](https://www.bytebase.com/blog/top-postgres-mcp-servers/) via search summaries.

### Inferences
- None of the adjacent systems provides Foundry's combination (typed objects + validated, permissioned, transactional actions + agent MCP on the same permission model) on Postgres. PostgREST/Supabase give the permission model (roles + RLS); Hasura gives actions and event triggers; Odoo gives the richest ready-made object/action/ACL model but is a monolith; metadata catalogs (Atlas, OpenMetadata, DataHub) describe objects rather than act on them.
- For Substrate (single Postgres, pgmq, roles, RLS, append-only record), the cheapest pattern is to copy: object type = table or `kind` rows with JSON schema; link type = FK/edge table; action type = a SQL function (SECURITY INVOKER, run as the caller's role) with parameter schema, validation, and writing an event row plus pgmq message; the agent's MCP tool list is generated from the action registry and connects as the agent's own Postgres role. That is a design inference, not something any single source states.
- PostgREST (MIT, Haskell, one binary, calls Postgres functions as RPC) is the one item that could be plugged in as-is as an HTTP layer over this design; MCP would still need to be written.

- Official Supabase MCP server licence/repo and tool set not verified; NocoDB MCP page and Baserow RBAC scope not read; Hasura DDN v3 licence not checked; Neo4j/TypeDB MCP status not checked; Budibase and Appsmith agent support not checked; Wikibase LICENSE text not read; PostgREST docs not fetched (429).
- No independent (non-vendor) review comparing these to Foundry's Ontology found.
